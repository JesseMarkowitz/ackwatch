The machine-readable Gate 4 report repeats these evidence groups in
`artifacts/reports/gate4-summary.json` after `npm run check:gate4`. That report derives its
per-step results from markers each step records as it passes, and it fails when the Matrix run
reports a browser error outside the documented rig noise, so a green summary cannot outrun its
evidence.

Two Phase 4 fault-injection items named in the implementation plan are not claimed here. A genuine
cross-origin webhook denial is not exercised: the loopback receiver suites run outside the browser,
so CORS refusal is covered by the transport's failure classification rather than by a real
preflight rejection. The optional developer-provided homeserver run is explicitly skipped rather
than passed when credentials are absent.

| §8.2 scale       | `artifacts/reports/scale-summary.json` via `npm run test:scale`                                    | Measured on real IndexedDB in Chromium. At the plan's stress ceiling (10,000 / 1,000) command (41 ms) and steady-state scheduler (228 ms) meet their targets comfortably. Per ingested event **straddles** its 50 ms target rather than sitting on one side of it: repeated runs of the same ladder have spanned roughly 27-64 ms, a better-than-twofold swing across identical input, with most runs over target. The per-run figures accumulate in `artifacts/reports/scale-history.jsonl`, which is the source of truth rather than any count written here — a sentence that enumerates samples is stale by the next run. A single sample is not evidence either way here, and the accepted deviation stands on that spread, not on the worst number. `artifacts/reports/scale-history.jsonl` accumulates one line per run so the Gate 5 report characterises the spread rather than quoting whichever run it last read. The remaining cost is validating every item on each refresh. The first scheduler pass after a backlog costs ~2.5 s materializing it, against ~250 ms for those that follow, and the recurring pass is the one that runs every 15 seconds. Render is measured with a forced React commit (`flushSync`) and a forced layout read, in two parts. **Mount** — what a page load pays once for a queue that already holds 1,000 cards — is load-sensitive, measuring 402, 408, 567 and 660 ms across runs. **Re-render** — what the app pays after every ingested event and every command — is 119.7 ms median at 1,000 items (samples 99–143 ms), measured the way the app actually behaves: `uiProjection` re-parses every row through zod, so React receives all-new objects even for unchanged items, `QueueCard` carries no `React.memo`, and the lists are neither virtualized nor windowed, so every card reconciles every time. Neither has a §8.3a threshold. The consequence worth naming: `commandMs` (63 ms) stops at the projection query, before React, so **per-event UI latency is ~183 ms — about two-thirds of it render** — which puts sustained throughput near 5 events/second at a 1,000-item queue. At a realistic 200-item session both halves fall proportionally. **Every render figure recorded before 2026-09-03 (11.2 ms, 19.5 ms) timed a render that crashed**: the benchmark's snapshot fixture was cast with `as unknown as AppSnapshot` and had drifted from the required `session` field, and React 19 reports such an error through `reportError` instead of throwing, so `flushSync` returned and the harness timed a tree that never mounted. |
